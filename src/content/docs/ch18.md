> 一句话：新一代模型更需要的是清晰的上下文结构，而不是越来越长、越来越硬的规则清单。

---

2026 年 7 月，Anthropic 发布了一篇很值得 OpenClaw 用户阅读的官方博客：[The new rules of context engineering for Claude 5 generation models](https://claude.com/blog/the-new-rules-of-context-engineering-for-claude-5-generation-models)。

这篇文章的核心观点很简单，但影响很大：**Claude 5 这一代模型变强后，旧式“堆规则”的 Prompt 工程开始失效，甚至会拖后腿。**

Anthropic 在 Claude Code 内部做了一个很激进的实验：他们为 Claude Opus 5、Claude Fable 5 这类新模型删除了 Claude Code 系统提示词中超过 80% 的内容，结果在编码评测上没有可测量的性能下降。

这说明一个趋势：

```text
旧时代：靠更多规则约束模型
新时代：靠更好的上下文结构释放模型判断力
```

这正是 OpenClaw 用户需要掌握的能力：不是把 Agent 的提示词越写越长，而是学会组织 System Prompt、AGENTS.md、SOUL.md、USER.md、MEMORY.md、Skills、工具描述和参考文件之间的关系。

---

## 18.1 什么是上下文工程

很多人把 Agent 的效果差归因于“模型不够强”或“Prompt 没写好”。但在真实系统里，用户输入只是一小部分。

一个 OpenClaw Agent 每次回复时，可能同时受到这些上下文影响：

- 系统提示词：决定 Agent 的基础身份、边界和运行规则
- `AGENTS.md`：工作区级别的行为规范
- `SOUL.md`：Agent 的人格、语气和定位
- `USER.md`：用户偏好、称呼、时区、长期背景
- `MEMORY.md`：长期记忆和重要经验
- `memory/YYYY-MM-DD.md`：近期日记和事件记录
- Skills：特定任务的操作手册
- Tool descriptions：工具自身的参数、行为和限制
- 当前会话：用户刚刚说的话、上下文历史和附件
- 项目文件：代码、配置、文档、测试、设计稿

**上下文工程**就是设计这些信息如何被组织、加载、压缩、拆分和更新。

它不是单句 Prompt 技巧，而是 Agent 的信息架构设计。

## 18.2 旧规则为什么会失效

旧式 Agent 配置常见的问题是：越用越长，越长越乱。

一开始你只写几条规则：

```markdown
- 回复要简洁
- 不要删除文件
- 不要乱发消息
```

后来踩坑多了，就不断往里加：

```markdown
- 不要写多行注释
- 不要生成计划文档
- 不要改 package-lock.json
- 不要主动创建文件
- 先读 README
- 每次都要跑测试
- 绝对不要使用某某命令
```

再后来，`AGENTS.md`、`MEMORY.md`、Skill、工具描述里都开始重复这些规则。

结果是：

1. **上下文变臃肿**：模型需要花更多注意力读无关信息。
2. **规则互相冲突**：一个地方说“不要写注释”，另一个地方说“复杂逻辑必须注释”。
3. **模型判断力被锁死**：明明当前任务需要例外处理，但硬规则不允许。
4. **维护成本越来越高**：没人记得哪条规则为什么存在。

Anthropic 把这种状态称为 overconstraining，也就是过度约束模型。

对旧模型来说，很多硬规则曾经是必要的；对更强的新模型来说，过多规则反而会成为“上下文债务”。

### Claude Opus 5 发布后的具体变化

Anthropic 在 Claude Opus 5 发布后，还同步更新了几份官方资料，可以把它们看成“模型能力变化以后，系统提示词和上下文策略应该怎么跟着变”的补充材料：

- [Introducing Claude Opus 5](https://www.anthropic.com/news/claude-opus-5)
- [What's new in Claude Opus 5](https://platform.claude.com/docs/en/about-claude/models/whats-new-opus-5)
- [Prompting Claude Opus 5](https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-opus-5)
- [System Prompts](https://platform.claude.com/docs/en/release-notes/system-prompts)

这些资料里有几条对 OpenClaw 用户很有参考价值。

第一，**Claude Opus 5 的上下文窗口变成 1M tokens**，而且官方强调它在长上下文里的指令跟随、工具调用和推理更稳定。更大的上下文不等于可以无限塞垃圾信息。恰恰相反，上下文越大，越需要做好结构化：哪些是长期记忆，哪些是任务资料，哪些是工具说明，哪些是临时会话状态，要分清楚。

第二，**thinking 默认开启**。Opus 5 会自己决定什么时候思考、思考多少，`effort` 参数变成控制推理深度的重要旋钮。这意味着很多旧 prompt 里“请仔细思考”“先自检一遍”“最后再验证一次”的脚手架可能要删掉，否则会叠加成过度思考和过度验证。

第三，**模型会更主动验证自己的工作**。Anthropic 明确说，如果旧提示词里写着“任何非平凡任务都要最终验证”或“用 subagent 再验证一次”，在 Opus 5 上可能导致 over-verification。对 OpenClaw 来说，更好的写法不是每次都强制验证，而是要求“完成前做最小有意义验证”，比如测试、构建、截图、diff、日志检查，选一个真正匹配任务的证据。

第四，**模型更愿意生成较长回复和进度说明**。Opus 5 在 agentic work 里更容易主动说明自己要做什么、正在做什么。产品化 Agent 如果不想变啰嗦，需要明确沟通节奏：第一次工具调用前一句话说明计划；过程中只有发现重要信息或改变方向才更新；结束时先说结果。

第五，**模型更愿意调用 subagent**。这对多 Agent 系统是好事，但也会增加成本和耗时。OpenClaw 里的规则应该写清楚：只有任务足够大、彼此独立、适合并行时才开 subagent；小任务不要为了“显得严谨”而委派。

第六，**官方公开的 System Prompts 页面说明了一个边界**：Claude Web 和移动端有自己的系统提示词，用于提供当前产品信息、语气、格式、安全边界等；这些更新不适用于 Claude API。对 OpenClaw 用户来说，这提醒我们：不要把 claude.ai 的产品级系统提示词照搬到自己的 Agent，应该提炼它的设计原则，再结合自己的 workspace、渠道、工具和用户场景重写。

可以把这些变化总结成一条迁移原则：

```text
模型越强，Prompt 越不应该写成“弥补模型缺陷的补丁包”。
它应该变成“告诉模型当前产品、用户、工具、边界和可用资料在哪里”的上下文地图。
```

## 18.3 新规则一：少写硬规则，多让模型判断

Anthropic 在博客里给了一个很典型的例子。

旧提示词会写：

```text
默认不要写注释。不要写多段 docstring。不要创建计划、决策或分析文档，除非用户明确要求。
```

这类规则看似安全，但问题是它不总是对的。

有些复杂代码确实需要注释；有些长期任务确实需要计划文档；有些项目本身就有大量 docstring 风格。

新写法更像这样：

```text
写出来的代码要像周围代码：匹配它的注释密度、命名方式和代码习惯。
```

这句话没有列出一堆禁令，而是把判断标准交给模型：看周围代码，然后模仿项目风格。

在 OpenClaw 里，这意味着你应该少写这种规则：

```markdown
- 永远不要写注释
- 永远不要创建新文件
- 永远不要修改配置
```

更好的写法是：

```markdown
- 修改代码时保持和现有代码一致，包括命名、注释密度、目录结构和错误处理方式。
- 涉及破坏性或外部副作用的操作先征求用户确认。
- 能通过测试、构建或直接检查验证的任务，完成前优先做最小验证。
```

这类规则给的是原则和边界，而不是把每个场景都写死。

## 18.4 新规则二：少堆工具示例，多设计好工具接口

过去的 Prompt 工程常说：要给模型大量 examples。

但 Anthropic 的新经验是：对更强的模型来说，过多示例可能会把模型锁进一个很窄的探索空间。

工具设计比工具示例更重要。

比如一个待办工具，如果参数是这样：

```json
{
  "step": "写文章",
  "status": "in_progress"
}
```

并且 `status` 只允许：

```text
pending | in_progress | completed
```

模型不用看十个例子，也能理解这个工具怎么用。

这对 OpenClaw Skill 和工具设计很关键。

好的工具/Skill 描述应该做到：

- 参数名字清楚
- 可选值明确
- 副作用写清楚
- 什么时候该用、什么时候不该用写清楚
- 不靠大量例子硬灌

坏的工具描述长这样：

```markdown
你可以用这个工具做很多事情。比如用户问 A 时这样做，问 B 时那样做，问 C 时再这样做……
```

好的工具描述更像：

```markdown
用于更新当前任务计划。只在多步骤任务中使用。最多一个步骤处于 in_progress。简单单步任务不要使用。
```

这就是“接口即提示词”。

## 18.5 新规则三：不要把所有信息塞到前面

很多人写 Agent 配置时，会把所有可能用到的内容都塞进 `AGENTS.md` 或系统提示词里。

这是最常见的上下文工程错误。

Anthropic 的建议是使用 **progressive disclosure**，也就是渐进式披露：

```text
常用、短小、总是需要的信息 → 放主上下文
复杂、低频、任务专用的信息 → 拆成 Skill 或独立文件，需要时再加载
```

在 OpenClaw 里可以这样分层：

```text
AGENTS.md
  放工作区通用规则：安全边界、记忆规则、文件组织方式

SOUL.md
  放 Agent 人格、语气、定位

USER.md
  放用户长期偏好：称呼、时区、项目背景

MEMORY.md
  放长期重要事实、教训和偏好

Skills
  放特定任务的操作流程：浏览器自动化、搜索、部署、生成图片等

references/
  放长文档、范例、rubric、检查清单、API 细节
```

不要把 Skill 的完整流程复制进 `AGENTS.md`。

`AGENTS.md` 只需要告诉 Agent：遇到某类任务时去读某个 Skill。

## 18.6 新规则四：不要重复自己

很多旧式 Prompt 会在多个地方重复同一条规则。

例如：

```text
系统提示词：使用浏览器前先 snapshot。
AGENTS.md：浏览器操作必须先 snapshot。
Skill：第一步先 snapshot。
工具描述：建议先 snapshot。
```

这种重复有两个问题：

1. 浪费上下文窗口。
2. 一旦其中一个版本过时，就会产生冲突。

更好的方式是让每类信息只出现一次：

- 工具怎么用：写在工具描述或对应 Skill 里
- 用户偏好：写在 `USER.md` 或 `MEMORY.md`
- Agent 性格：写在 `SOUL.md`
- 项目 gotchas：写在项目级文档
- 安全边界：写在高优先级、稳定的位置

上下文工程不是“多写几遍让模型记住”，而是“放在正确的位置，让模型需要时能找到”。

## 18.7 新规则五：CLAUDE.md / AGENTS.md 要轻

Anthropic 特别提醒：不要把 CLAUDE.md 当成所有知识的中央仓库。

同理，在 OpenClaw 里，不要把 `AGENTS.md` 写成百科全书。

`AGENTS.md` 最适合写：

- 这个 workspace 的定位
- 每次启动必须读哪些文件
- 记忆如何记录
- 哪些操作必须先问
- 文件组织习惯
- 常用 Skill 的入口说明

不适合写：

- 大段 API 文档
- 完整部署手册
- 每个项目的全部背景
- 每个工具的全部参数
- 几十条互相重叠的行为禁令

一个健康的 `AGENTS.md` 应该像新员工入职手册的目录，而不是公司全部制度的汇编。

## 18.8 新规则六：长期记忆不要塞进项目规则

Anthropic 提到，Claude 现在更依赖自动记忆，而不是把所有记忆都写进 CLAUDE.md。

OpenClaw 本来就适合这种分层：

```text
USER.md
  用户长期稳定资料：称呼、时区、业务背景

MEMORY.md
  策展后的长期记忆：偏好、决策、教训、重要项目状态

memory/YYYY-MM-DD.md
  当天流水账：发生了什么、临时上下文、待整理素材
```

不要把这些内容全写进 `AGENTS.md`。

错误示例：

```markdown
# AGENTS.md
用户上周说喜欢 A。
昨天部署 B 失败。
某次搜索发现 C 是错的。
下周三要提醒 D。
```

更好的做法：

- 用户稳定偏好 → `USER.md`
- 长期教训 → `MEMORY.md`
- 当天事件 → `memory/YYYY-MM-DD.md`
- 定时提醒 → cron / TaskFlow / 自动化任务

这样上下文不会变成一锅粥。

## 18.9 新规则七：Reference 可以比描述更强

Anthropic 还强调：新模型可以处理更丰富的 reference，不再只依赖简单 Markdown spec。

Reference 可以是：

- 测试文件
- HTML mockup
- 设计稿导出的结构化文件
- 另一个代码库里的实现
- API 返回样例
- 评审 rubric
- 真实日志
- 用户反馈截图

对代码任务来说，**代码形式的 reference 往往比自然语言描述更高保真**。

例如，与其这样说：

```text
请做一个和现有页面风格类似的设置页。
```

不如直接给：

```text
参考 src/pages/profile/settings.tsx 的布局和交互方式，新建 billing settings 页面。
```

与其描述接口格式，不如给一段真实 JSON：

```json
{
  "id": "evt_123",
  "type": "payment.succeeded",
  "created_at": "2026-07-26T12:00:00Z"
}
```

Reference 的价值在于减少口头解释，把模型对齐到真实材料。

## 18.10 一个 OpenClaw 上下文分层模板

下面是一个适合个人全能助手的上下文分层模板。

```text
workspace/
├── AGENTS.md
├── SOUL.md
├── USER.md
├── MEMORY.md
├── HEARTBEAT.md
├── TOOLS.md
├── memory/
│   ├── 2026-07-26.md
│   └── heartbeat-state.json
├── skills/
│   ├── search-layer/
│   │   ├── SKILL.md
│   │   └── references/
│   ├── browser-automation/
│   │   └── SKILL.md
│   └── deploy-checklist/
│       ├── SKILL.md
│       └── references/
│           ├── cloudflare.md
│           └── github-actions.md
└── projects/
    └── openclaw-guide-zh/
```

每个文件负责的事情要清楚：

```text
AGENTS.md：工作区宪法
SOUL.md：Agent 是谁，怎么说话
USER.md：用户是谁，有什么长期偏好
MEMORY.md：长期重要记忆和经验教训
HEARTBEAT.md：心跳任务的短清单
TOOLS.md：本地工具、账号、服务器等操作备注
skills/*/SKILL.md：某类任务的入口手册
skills/*/references/：长资料、范例、检查清单
```

只要职责分清，Agent 就不需要靠一大段“超级 Prompt”硬撑。

## 18.11 如何给现有 Agent 做上下文瘦身

可以按这个顺序检查你的 OpenClaw workspace。

### 第一步：找重复

搜索这些文件里是否重复表达同一条规则：

```text
AGENTS.md
SOUL.md
USER.md
MEMORY.md
TOOLS.md
skills/*/SKILL.md
```

如果同一条规则出现三次，只保留最合适的位置。

### 第二步：找冲突

重点找这些冲突：

- 一个地方说“回复要简洁”，另一个地方要求“详细解释每一步”
- 一个地方说“不要主动运行命令”，另一个地方说“能做就直接做”
- 一个地方说“不要写文件”，另一个地方说“必须记录到 memory”
- 一个地方说“不要搜索”，另一个地方说“不确定必须搜索”

冲突不是小问题。模型会浪费注意力在解释冲突上，而不是完成任务。

### 第三步：找过时

很多规则是因为一次事故写下的，但后来系统能力、工具或流程已经变了。

过时规则要么删除，要么改成更通用的原则。

### 第四步：把长内容拆出去

如果 `AGENTS.md` 里某一段超过 100 行，通常就该考虑拆成 Skill 或 reference。

例如：

```text
浏览器自动化细节 → browser-automation skill
部署流程 → deploy skill
新闻搜索流程 → search-layer skill
内容发布格式 → publishing skill
```

### 第五步：保留真正重要的“硬边界”

不是所有硬规则都要删除。

这些规则应该保留，而且要写清楚：

- 不泄露私密信息
- 外发消息、发布内容、删除文件前要确认
- 破坏性命令必须征求用户同意
- 不确定事实必须查证
- 用户明确要求的格式必须遵守

瘦身不是放弃安全，而是删除低价值、重复、过时、互相冲突的约束。

## 18.12 写 Skill 时的上下文工程原则

Skill 是 OpenClaw 里最适合承载复杂流程的地方。

一个好的 Skill 应该：

1. **入口判断明确**：什么任务触发这个 Skill。
2. **流程短而清楚**：主流程不要写成几十页。
3. **长资料拆 references**：不要把所有细节塞进 `SKILL.md`。
4. **少写绝对禁令**：除非涉及安全、隐私、外部副作用。
5. **让工具接口自解释**：参数名、枚举值和副作用比示例更重要。
6. **写失败恢复策略**：工具失败时怎么换路，而不是直接甩锅用户。
7. **保留验证门槛**：完成前用测试、构建、截图、diff 或检查输出验证。

一个常见结构是：

```text
my-skill/
├── SKILL.md
└── references/
    ├── checklist.md
    ├── examples.md
    └── troubleshooting.md
```

`SKILL.md` 只写入口、流程和关键规则；长例子放 `references/`。

## 18.13 推荐写法和不推荐写法

不推荐：

```markdown
你必须永远保持简洁。你必须永远不要写注释。你必须永远不要创建文件。你必须每次都先问用户。你必须每次都完整解释你的思考过程。你必须永远不要使用浏览器，除非用户说“浏览器”。
```

问题：绝对化、互相冲突、场景不分。

推荐：

```markdown
默认保持回复简洁。需要解释权衡、风险或复杂步骤时再展开。

修改代码时遵循现有项目风格，包括命名、注释密度、目录结构和测试习惯。

可逆、低风险的本地操作可以直接做；删除、发布、外发消息、改权限等高风险操作先确认。

不确定的事实先查证；涉及当前状态的内容优先使用工具获取证据。
```

这类写法给 Agent 留出了判断空间，同时保住了安全边界。

## 18.15 小结

Anthropic 这篇博客真正想表达的不是“Prompt 不重要了”，而是：**Prompt 不应该继续承担所有上下文职责。**

对 OpenClaw 来说，可以总结成几条实践原则：

1. 少写硬规则，多写判断原则。
2. 少堆示例，多设计清楚工具接口。
3. 少把信息塞前面，多做渐进式加载。
4. 少重复指令，避免上下文冲突。
5. `AGENTS.md` 保持轻量，复杂流程交给 Skills。
6. 长期记忆放 `MEMORY.md`，流水账放 `memory/`。
7. 多用真实 reference：代码、测试、日志、mockup、rubric。
8. 定期清理上下文债务。

一句话收尾：

```text
不要把 Agent 的上下文写成十诫石碑。
把它设计成一棵清晰、可维护、按需加载的知识树。
```

这才是 Claude 5 时代，也同样是 OpenClaw 多 Agent 时代，更可持续的上下文工程。
